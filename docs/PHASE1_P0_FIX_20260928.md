## Root causes and behavior changes

| Issue | Exact root cause / before | After |
|---|---|---|
| Shipping fee lifecycle | `ShippingFeesService.collectAt` accepted only `COLLECTED` or `PAID` when checking sender fees at delivery. Remittance/settlement advanced the same ledger row to `REMITTED`/`SETTLED`, so a valid payment failed with `SHIPPING_FEE_NOT_COLLECTED`. Collection retries also only recognized `COLLECTED`. | `assertObligationSatisfied` is the single backend evidence policy. Cash states require the exact immutable amount, collector and collection timestamp. Remitted/settled states additionally validate remittance evidence and collector/remitter agreement; settled requires settlement actor/time. Online `PAID` uses the existing payment integrity validator. Unpaid, pending payment, cancelled, disputed and inconsistent evidence remain blocked. Sender delivery never recollects; receiver delivery retries after remit/settle still require the original exact amount and collector. No ledger/history rewrite. |
| Login versus password change/reset | Login read User and verified its old hash, then inserted AuthSession outside the credential-change transaction. A reset/change could increment tokenVersion and revoke existing sessions before this insert; refreshing the late session then used the new User version. | Session creation locks the User row, rereads current hash/tokenVersion/ACTIVE status and validates the verified snapshot in the same transaction as the insert. Refresh takes the same User-first lock and validation before its existing conditional session revocation/rotation. Change/reset already update User before revoking sessions. Either session commits first and is revoked by the credential mutation, or mutation commits first and stale login/refresh is rejected. Token generation, cookie contract and single-use rotation remain intact. |
| Public transfer notes | Transfer dispatch appended `WarehouseTransfer.note` to a PUBLIC TrackingEvent description; receive appended DTO note. Public tracking used raw descriptions, and cache hits returned prebuilt payloads. | New transfer PUBLIC descriptions contain lifecycle text only. One `mapPublicTimeline` projection replaces descriptions for both affected event types, including old PostgreSQL records and pre-fix public/customer caches. Customer timeline also filters PUBLIC visibility on database projection. Warehouse transfer notes remain in the scoped transfer API; receipt notes remain in Admin-only audit `after.note`. |
| Delivery audit entity ID | `DeliveryService.trackAudit` hardcoded `entityType='Shipment'` but accepted a caller-supplied entityId. Complete/fail passed `attempt.id`; assignment/start passed assignment IDs; return-start also passed an attempt ID. Shipment-ID searches therefore missed these records. | The helper always writes `shipment.id`, with `assignmentId`/`attemptId` in metadata. Exact shipment UUID searches also match legacy records through actual DeliveryAttempt/DriverAssignment relations, constrained to the affected action allowlist and `entityType='Shipment'`. Other audit filters/pagination remain. Returned legacy rows retain their original entityId. |
| Zero fee | Pricing input/database allowed baseFee=0; calculation could return totalFee=0, while the fee service and existing `ShippingFeeTransaction_expectedAmount_check` require >0. Quote could succeed while shipment creation failed later. | User decision: zero total fee is unsupported. New config DTO requires baseFee>=1; variable fees can remain zero. Pricing calculation rejects nonpositive/non-safe-integer totals with HTTP 409 `PRICING_TOTAL_FEE_INVALID`, including legacy configs/discounts, before quote or shipment persistence. Admin form minimum/error/helper agree. Existing configurations/snapshots are not changed. |

## Historical data and compatibility

**Migration required: NO.** No schema or migration file changed. The local runner replayed existing canonical migrations into fresh, disposable local databases only; it did not run migrate deploy against staging/production.

- Tracking history: preserve original rows, IDs, timestamps and descriptions. Public/customer reads substitute safe lifecycle descriptions for the two transfer types. This deliberately removes embedded warehouse-detail/free-text descriptions from those public entries while preserving their titles, statuses, order and IDs. No parsing of arbitrary note delimiters, no silent history update. Existing Redis entries are projected again on read, so waiting for TTL expiry is unnecessary for these notes.
- Internal notes: transfer note is available through the existing role/warehouse-scoped transfer list. Receive note is available through the existing Admin audit API. No new staff permission or public note field was introduced. Raw legacy TrackingEvent descriptions remain in PostgreSQL; the dispatcher shipment detail API does not expose a timeline.
- Audit history: no UPDATE/backfill. Exact shipment UUID search resolves only proven FK relationships and known actions. Unrelated actions are excluded; orphaned/missing relations are not guessed. A future persistent correction, if needed, must first export affected audit IDs and relation evidence, review mismatches, then use an explicit, separately reviewed append-only correction plan.
- Fee APIs, enums, response shapes, ledger amounts, COD amounts, ownership and idempotency keys remain compatible. Invalid evidence remains an error. Previously valid reconciled fees now allow delivery/retry.
- Auth response/cookie/JWT format remains compatible. Existing sessions are not globally revoked by deployment. Requests that lose a credential race now receive the existing authentication error instead of a fresh session. This change prevents future races; it does not retrospectively identify sessions issued by the old bug.
- Pricing intentionally tightens validation: baseFee=0 in new configuration requests now returns 400. Legacy configurations producing nonpositive totals return 409 and require an explicit Admin configuration update. Immutable historical shipment prices are untouched. Database pricing constraints remain compatible with historical rows; the existing fee-table >0 constraint remains authoritative at persistence.
