## F04 — Notification enqueue recovery

**Root cause:** Notification was committed in PostgreSQL before a best-effort BullMQ enqueue. There was no persisted delivery intent or scanner. A crash or Redis failure in that gap left the in-app record intact but could permanently lose realtime/email work. Email enqueue also depended on completion of the realtime worker.

**Design:** A `NotificationDelivery` outbox has one unique row per `(notificationId, channel)` for REALTIME and EMAIL. `NotificationsService.createIdempotent` writes both intents in the same transaction as the notification, using the existing duplicate-safe notification identity. Outbox state is separate from Notification API content and deep-link data.

- `completedAt IS NULL` identifies unfinished work. `enqueuedAt`, `enqueueAttempts`, `nextAttemptAt`, `lastError` and `skippedReason` distinguish queue acknowledgement, retry eligibility and deliberate skips.
- Startup and a five-second timer reconcile due work. Each atomic PostgreSQL claim uses `FOR UPDATE SKIP LOCKED`, limits the batch to 50 intents, and persists exponential backoff of 10/20/40/80/160/300 seconds before contacting Redis. No database lock is held across Redis or SMTP I/O.
- A crash before publish, after claim, or after Redis acknowledgement leaves an unfinished PostgreSQL intent discoverable on a later scan/restart. Missing Redis jobs are recreated even if an earlier enqueue was acknowledged.
- Existing active/waiting/delayed jobs retain BullMQ's five attempts and exponential one-second retry. Exhausted/completed queue records whose PostgreSQL intent is still unfinished can be retried after the persisted reconciliation backoff.
- SMTP disabled/ineligible notifications are deliberately completed with a skip reason, preserving current email eligibility behavior. Password-reset jobs keep their existing separate flow.

**Idempotency:** PostgreSQL's composite key prevents duplicate durable intents; stable `notification-<id>` / `email-<id>` BullMQ IDs prevent ordinary duplicate queue jobs, including concurrent reconcilers. Workers check persisted completion before effects. Email retains `emailSentAt`, its conditional claim, and a stable SMTP Message-ID. Replaying a completed job does not resend a completed notification.

**Delivery semantics:** SMTP and Socket.IO are external effects, so a crash after an effect but before its database acknowledgement still has at-least-once semantics. A stable Message-ID is not a recipient-side exactly-once guarantee. Realtime retries carry the same notification ID; the existing UI invalidates/refetches the durable notification list rather than appending another durable notification. Offline realtime delivery continues to rely on the Notification Center on reconnect.

**Migration required: YES.** `20261007120000_notification_delivery_outbox` adds one enum, one table, its FK/key/index and historical delivery metadata. The need/schema was reported before implementation. The manifest appends only the new SQL checksum; old migration bytes, checksum exceptions and provider lock are unchanged.

Historical realtime cannot be classified reliably, so it is marked complete with `LEGACY_REALTIME` without replay. Existing `emailSentAt` completes the corresponding historical email intent; unsent email remains eligible for reconciliation and existing worker rules. Notification content/read state is not rewritten. The optional historical-realtime question received no selection; the stated default was used.

The single additive migration was applied only to the pre-existing disposable local database `p0_regression_1791224446659` at `127.0.0.1:55432`. Four historical Notifications produced eight intents; all four historical realtime intents were marked as legacy skips. No staging/production migration or migration-ledger rewrite was performed. A later release needs this migration before the new backend. Old binaries do not write the outbox, so an eventual cutover must drain old notification writers/workers during migration and application replacement to avoid an old-writer gap or overlapping old/new delivery workers. No cutover was performed here.

**Tests: PASS (8 PostgreSQL + real BullMQ integration cases).**

## F05 — COD pagination

**Root cause:** `/cod/dashboard` and `/cod/mine` returned only the newest 100 records without a page contract, leaving older transactions unreachable in the operational UI.

**Endpoints:** `GET /api/v1/cod/dashboard` (Admin), `GET /api/v1/cod/mine` (Driver).

| Query | Contract |
|---|---|
| `page` | Integer >= 1; default 1 |
| `limit` | Integer 1–50; default 20 |
| `status` | Optional PENDING / COLLECTED / REMITTED / SETTLED / DISPUTED |
| `payoutStatus` | Admin only: NONE / PENDING / SENT / PAID_OUT / DISPUTED; NONE means no payout exists |

Response preserves `items` and `summary`, and adds top-level `page`, `limit`, `total`, `totalPages`. `total` describes the filtered list. `summary` always covers the complete authorized dataset, independent of both pagination and list filters. Empty results have `totalPages: 0`.

Items sort by `createdAt DESC, id DESC`. Items/count/summary use one repeatable-read transaction. Driver reads and summaries are scoped to the authenticated collecting DriverProfile; payout records are omitted and payout filters are forbidden for Driver. Existing money calculations, remittance/payout commands and Shipping Fee behavior are unchanged.

**Frontend:** Admin and Driver COD pages use server pagination (20/page), visible totals, labeled COD status filters, and Admin payout filters. Filter changes return to page 1. Page and filters belong to the query cache key; summaries do not use page items. Loading/empty/error/retry states remain accessible. If another action/operator removes the final page from a filter, a visible “Về trang đầu” action provides recovery. The old “maximum 100” truncation text is removed.

**>100 evidence:** The PostgreSQL/HTTP suite creates 105 transactions for the owner and seven for another Driver. Equal creation timestamps deliberately exercise ID ordering. Owner pages return exactly 50/50/5, in expected order, with 105 unique IDs and no missing IDs. Every page has the same scoped 15,750,000 VND summary. Another Driver sees only their seven records.

Record 105 is fetched from page 3, rejected for the wrong Driver, then processed through real HTTP remit/retry, Admin receipt confirmation, settlement, payout creation/send and owning Customer confirmation. Status/payout filters find it at each stage; these COD actions do not create a Shipping Fee transaction. Filtering remaining COLLECTED records returns 104 IDs across pages while summary still includes SETTLED records.

Browser tests use the production COD page with intercepted test HTTP only. They reach page 6/record 105 at the frontend's page size 20, open its action modal and submit a handover, exercise every payout filter, verify stable full-dataset summaries, no page overlap, empty/error/retry behavior and recovery from a disappearing page. Layout passes at 375/768/1440px without viewport overflow. Existing COD UX regression covers all money acknowledgement actions at 375x812, 812x375, 768x1024 and 1440x900.

**Migration required: NO for F05.** Existing API item/summary shapes remain; consumers must adopt the new metadata to traverse beyond the default 20 rows. This frontend is updated in the same change.
