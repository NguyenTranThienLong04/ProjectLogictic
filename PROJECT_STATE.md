New staging uses a clean DB; legacy development H2/H3 remains blocked pending a separately reviewed data-preserving transition. Migration/deploy jobs run only in Linux/container, without disabling Windows Application Control.
- Refresh token là opaque token, chỉ lưu hash trong PostgreSQL và chỉ truyền bằng HttpOnly cookie; mỗi refresh rotate session atomically
- Access token bị vô hiệu khi session revoke, user suspend, role/tokenVersion đổi hoặc temporary password chưa đổi
- Password hash dùng Node scrypt với salt riêng; reset token chỉ lưu SHA-256 hash, one-time và có expiry
- Forgot-password trả response không phân biệt account tồn tại; raw reset token chỉ đi qua delivery boundary nội bộ, email delivery thuộc Phase 8
- Frontend keeps access tokens in memory and restores sessions through the refresh cookie; frontend role visibility never replaces backend authorization
- TypeScript khóa ở 6.0.3 để tương thích `typescript-eslint`
- Prisma runtime dùng pooled `DATABASE_URL`; migration dùng direct `DIRECT_URL`
- Redis chỉ là hạ tầng phụ trợ, không phải source of truth
- Saved addresses are always customer-scoped; a partial unique database index enforces at most one default address per customer under concurrency
- First saved address becomes default; deleting the default promotes the most recently created remaining address
- Phase 2 pricing policy is canonical in `docs/DOMAIN.md`: 30,000 VND includes first 1 kg; excess kg rounds up at 5,000 VND/kg; COD fee is `ceil(codAmount * 0.5%)`; distance/surcharge/discount are zero
- Pricing configuration is versioned; activating a new config is serializable and audited, while shipments retain immutable pricing snapshots
- Shipment creation requires a customer-scoped saved pickup address and client-generated idempotency UUID; retry returns the original shipment without duplicate tracking/audit history
- Cancellation is a dedicated command guarded by `CancellationPolicy`, conditional version update and append-only tracking/audit records; no generic status endpoint exists
- Driver rejection policy is canonical in `docs/DOMAIN.md`: reason required; assignment becomes `REJECTED`; shipment returns to `AWAITING_PICKUP_ASSIGNMENT`; driver availability is restored when eligible; AuditLog and idempotent notifications for active Dispatchers are mandatory
- Phase 3 schema applied via migration `20260817180000_phase3_dispatcher_pickup` with DB CHECK constraints for `DriverProfile` availability states and polymorphic `ShipmentProof` references
- Warehouse transfer dispatch clears `currentWarehouseId` (shipment in transit is not warehouse inventory); receive sets `currentWarehouseId` at destination; `WarehouseTransfer` is idempotent via `(createdById, clientRequestId)`; destination warehouse cannot receive transfers addressed elsewhere
- Prisma `relationJoins` is enabled so relation includes within interactive transactions execute as joined queries instead of concurrent queries on one PostgreSQL transaction connection
- Driver GPS sends every 5 seconds; Redis `driver:location:{driverId}` TTL is 20 seconds (4× interval) to tolerate transient mobile-network misses without showing false offline while expiring genuinely stale locations quickly
- COD collection is created atomically by `completeDelivery` only when `codAmount > 0`; remittance must exactly equal the shipment COD snapshot or becomes `DISPUTED`, and settlement is prohibited unless both collection/remittance equal expected amount.
- COD remittance and settlement enforce C10 with transactional conditional `updateMany` predicates and `count === 1`; retries may return the committed result idempotently, but only the winning transition writes an audit record.
- Shipping-fee collection is a separate one-row-per-Shipment ledger. The fee snapshot is collected only inside the owned pickup/delivery command, while COD continues to use only `Shipment.codAmount`; neither aggregate mutates the other.
- Shipping-fee remittance is owned by the collecting Driver and must exactly match the immutable fee snapshot. Admin settlement is legal only from `REMITTED`; disputes are append-only reasoned records resolved by an explicit command back to their captured `COLLECTED|REMITTED` source state. COD remains a separate aggregate throughout.
- Cache keys are canonical: `tracking:{trackingCode}` and `shipment:{id}:summary`; every shipment lifecycle mutation invalidates both after PostgreSQL commits.
- Notification rows are the durable delivery source; BullMQ only transports deterministic jobs. Queue/Redis failure cannot roll back or corrupt an already committed shipment transition (C13).
- Notification and email retries are idempotent through `(userId, eventKey)`, deterministic BullMQ job IDs, conditional email delivery claims, persisted `emailSentAt`, and deterministic SMTP `Message-ID` (C09).
- SMTP email delivery is disabled unless `EMAIL_DELIVERY_ENABLED=true` and valid SMTP settings are supplied; persisted in-app notifications and socket delivery remain active.
- Analytics date filters define a shipment cohort by `Shipment.createdAt` (maximum 366 days); optional warehouse/driver scope is applied in the PostgreSQL `filtered_shipments` CTE and reused by all metric families.
- Phase 9 analytics remains read-only and requires no schema migration; Recharts is isolated in a lazy-loaded route chunk.
- Warehouse, warehouse-staff, and driver optimistic concurrency uses integer `version` columns; shipment concurrency continues using its existing version guard.
- Redis degradation does not make readiness fail because Redis remains disposable infrastructure; PostgreSQL failure returns readiness HTTP 503.
- Request IDs are assigned in middleware before guards/throttling, accept only a bounded safe character set, and are included in response headers, API metadata/error bodies, and structured HTTP logs.
- GPS customer broadcasts use `shipment-location:{shipmentId}`; the general `shipment:{shipmentId}` room remains available for non-location shipment events.
- Role route modules are selected only after authentication; admin and dispatcher chunks may include warehouse/operations UI they are authorized to use, while unrelated role UI is not eagerly downloaded.
- Visual refactor uses the Operational Swiss system (Inter, blue tracking primary, orange operational/COD attention, dense 4px spacing rhythm, low motion); Tailwind theme tokens are the implementation source for shared visual primitives.
- `docs/UI.md` is the single product source for `StatusBadge` colors; shared config mirrors it and always renders a text label plus dot. Warehouse transfer `IN_TRANSIT` shares sky with Shipment transit for lifecycle consistency; Transfer/COD pending share orange but use different shades for operational urgency; Return stays amber instead of reusing orange.
- Dashboard metrics are calculated with PostgreSQL aggregate queries; Node only maps aggregate rows and bounded recent-record lists.
- `DAMAGED` and `LOST` are read/monitoring states in this closure. No UI or API may create those transitions until a canonical business command is documented.
- Driver detail and standalone Map reads resolve the authenticated driver profile at the backend; the Map reuses the existing Redis current-location key/TTL and does not change GPS or Socket contracts.
- Admin user suspension increments `tokenVersion` and is audited; a driver account with an active assignment cannot be suspended, and restoring the user does not silently restore driver availability.
- Applied migration history is corrected only when the repository SQL is proven equivalent to the existing development schema; the Phase 5 repair updated one successful resolved checksum and did not reset or mutate business data.
- Redis producer operations fail fast and remain isolated from committed PostgreSQL state; BullMQ workers may reconnect only after Redis completed an initial ready state, while startup-unavailable processes create no queue connections or reconnect timers.
- Production configuration never silently becomes development: `NODE_ENV` and `FRONTEND_URL` are required, production Redis is explicit and fail-fast, example JWT secrets are rejected, Swagger defaults off, and refresh cookies require the `__Secure-` prefix.
- Browser cookie-bearing auth requests with an Origin header must match the configured production frontend; JWT and Socket verification are restricted to HS256, and connected sockets cannot outlive access-token expiry.
- Password-reset tokens remain hash-only in PostgreSQL; the raw one-time token exists only in the short-lived BullMQ email job and is removed on completion, with deterministic Message-ID and retry/failure isolation.
- Prisma generation is build-time and does not need database secrets; migration commands use only `DIRECT_URL`, production startup never auto-runs migrations, and build success requires the runnable `dist/main.js` artifact.
- Frontend production config allows same-origin defaults but rejects localhost, insecure external URLs, and SIMULATION mode at build time; role boundaries and lazy route chunks remain unchanged.
- Local frontend API routing keeps `VITE_API_URL` optional: an explicit value is used as-is, while development-only same-origin `/api` requests proxy to `http://localhost:${PORT}`; production receives no Vite dev proxy or localhost fallback.
- DriverProfile candidate selection derives eligibility from paginated Admin Users (`DRIVER` + `ACTIVE`) and existing DriverProfile `userId` values; the create request still submits the unchanged backend `userId` contract and backend RBAC remains authoritative.
- Warehouse staff candidate selection derives eligibility from paginated Admin Users (`WAREHOUSE_STAFF` + `ACTIVE`) and staff profiles across all warehouses; assignment still submits the unchanged `userId`/`staffCode` contract, while the unique `WarehouseStaffProfile.userId` relation and backend RBAC remain authoritative.
- Current GPS remains disposable Redis state with no PostgreSQL fallback: read outages degrade to an honest no-current-location response, but writes fail closed and never emit a Socket update that was not stored; payload age validation mirrors the same 20-second TTL as a defense against stale keys.
- Driver operating area uses one nullable `operatingWarehouseId` relation: pickup service area is the normalized operating-Warehouse city, while delivery must match the exact destination Warehouse. Nullable storage keeps the migration additive; candidate eligibility fails closed until an active Warehouse is configured.
- Location-aware assignment has one backend policy for listing and command validation. Only current GPS younger than the canonical 20-second TTL is eligible; Haversine is an estimated straight-line distance used for ordering only, never route distance or ETA, and Dispatcher/Admin remain the decision-maker.
- Driver task-map targets are backend-authoritative and ownership-scoped: pickup snapshot for Pickup Detail, destination Warehouse before a delivery attempt, and receiver snapshot after delivery starts. Receiver coordinates remain absent from the pre-start delivery payload.
- Driver task maps reuse the authenticated current-location read and treat location age `>= 20s` as stale; stale Driver markers are hidden while the known task target remains visible. The 5-second GPS cadence, Redis TTL 20 seconds, and Socket event contract are unchanged.
- Navigation uses a provider-neutral product boundary implemented with a Google Maps directions URL that omits the Driver origin, so the provider may use device location with its own consent. The application does not own route generation, turn-by-turn guidance, route distance, or ETA.
- Warehouse origin scope is authoritative before check-in: pickup completion snapshots the eligible pickup Driver's operating Warehouse into `Shipment.originWarehouseId`; scan lookup/check-in validates that relation and never lets frontend warehouse selection define it.
- A WarehouseTransfer is created as `PENDING` and does not move its Shipment. Only the dedicated dispatch command transitions the transfer and Shipment to `IN_TRANSIT` and clears `currentWarehouseId`; Receive restores `currentWarehouseId` at the exact destination. PostgreSQL enforces at most one active transfer per Shipment.
- Shipping-fee payer is an immutable Shipment snapshot: Create Shipment requires `SENDER|RECEIVER`; legacy rows are backfilled to `SENDER`; payer changes neither pricing nor COD, and no update command or generic endpoint may mutate it after create.
- Browser E2E simulation remains a real integration boundary: `VITE_LOCATION_MODE=SIMULATION` sends GPS through the authenticated API, Redis TTL storage, and Socket.IO; tests never inject frontend-only location state or bypass backend authorization.
- Driver specialization uses a non-empty multi-value `DriverProfile.capabilities` set (`PICKUP|DELIVERY|LINE_HAUL`) under the existing `DRIVER` role. Legacy/new profiles default to pickup + delivery; command policies enforce the required capability at the backend.
- Existing DriverProfile vehicle fields remain the last-mile vehicle description. `LineHaulVehicle` is an independent fleet record with unique normalized code/plate and no hard-delete path; only `AVAILABLE` vehicles may be scheduled/prepared/dispatched, future reservation keeps `AVAILABLE`, Dispatch sets `IN_USE`, and arrival releases it to `AVAILABLE`.
- Line-haul resource ownership is time-bounded for `PLANNED`: PostgreSQL half-open range exclusion constraints prevent overlapping Driver/Vehicle reservations while allowing adjacent windows. `READY|IN_TRANSIT` are execution ownership; the independent WarehouseTransfer partial unique constraint continues preserving one active manifest association.
- `LineHaulTripTransfer` preserves manifest association history without replacing WarehouseTransfer. Manifest is mutable only in `PLANNED`; READY locks it. Trip dispatch reuses the canonical WarehouseTransfer lifecycle in the same transaction, while arrival stays separate from destination receive.
- A Driver cannot simultaneously execute a `READY|IN_TRANSIT` line-haul trip and an active pickup/delivery assignment, even with multiple capabilities. A future PLANNED reservation is not execution ownership; READY/Dispatch and last-mile assign commands revalidate under a Driver row lock.
- `ARRIVED` is the terminal trip state; there is no G2 `COMPLETED`. Arrival by Admin or active destination Warehouse Staff records the vehicle at destination and releases it, while each package remains `IN_TRANSIT` until its transfer is explicitly received.
- Line-haul current GPS is isolated by trip key/room/event from last-mile Driver GPS. Writes are accepted only for the authenticated active LINE_HAUL owner while `IN_TRANSIT`; map reads preserve Admin/Dispatcher and origin/destination Warehouse scope and never expose line-haul coordinates to Customers.
- Line-haul map freshness uses the same 5-second cadence and 20-second TTL as Phase 6. Arrival makes PostgreSQL visibility inactive first, then best-effort removes Redis state and emits `linehaul.trip.ended`; Redis failure cannot roll back or revive trip lifecycle.
- Route metrics use one provider-neutral backend boundary. `ROAD_ROUTE` has provider distance + planned duration; `HAVERSINE_FALLBACK` has straight-line distance and `durationSeconds = null`. Provider/cache failure never changes eligibility, ownership or Trip lifecycle.
- Candidate route calls happen only after Phase B eligibility/GPS checks, are pre-sorted by Haversine, capped at 4 concurrent/20 external attempts, and cached for 900 seconds using provider/mode plus coordinates rounded to 4 decimals. Redis remains disposable.
- Line-haul planned route metrics are nullable historical snapshots written only by the first successful `PLANNED → READY` transition. Dispatch/arrival never recalculate them; remaining ETA is on-demand from current authorized G3A GPS and is not traffic-aware.
- Until a production provider is explicitly approved, environment validation requires `ROUTE_PROVIDER=DISABLED` in production. Development can explicitly evaluate an OSRM endpoint without an API key; no public arbitrary route proxy or frontend credential exists.
- Route geometry is a vendor-neutral bounded point list; business/UI layers never parse encoded polylines or upstream schemas. Planned v1 and every reroute are append-only PostgreSQL history, while `currentRouteId` is the only authoritative route pointer.
- Deviation is operational Redis state, not a Trip/Shipment lifecycle status. It requires current GPS plus current-route geometry and three consecutive samples beyond the configured 500 m threshold; missing/stale GPS, missing geometry, disabled provider or Redis uncertainty produces `UNKNOWN`.
- Reroute authority is Admin/Dispatcher only. The command always routes captured current GPS to the existing destination, calls the provider outside the transaction, then commits with optimistic version/current-route/destination checks; failure or concurrency leaves the current route untouched.
- Line-haul capacity uses integer grams end to end. `verifiedWeightGrams` in the immutable post-check-in Shipment package snapshot is authoritative, with legacy fallback to snapshot `weightGrams`; active `LineHaulTripTransfer` rows are the only manifest contributors.
- Fleet legacy capacity is never guessed or treated as infinite. Nullable storage keeps migration additive, while new create/update, activation, eligibility and trip transitions require a positive value.
- All manifest mutations lock the trip row before recomputing load. `prepareTrip` and `dispatchTrip` revalidate capacity under the same execution locks; READY snapshots manifest weight and vehicle capacity once so later Fleet edits cannot rewrite trip history.
- Utilization percent and the 80% near-full threshold are presentation-only. Backend overload decisions compare integer `manifestWeightGrams <= capacityWeightGrams`; dimensions exist but volume/bin-packing policy is deliberately outside G3C1.
- Line-haul schedule mutations are separate `schedule/reschedule/unschedule` commands and never a generic trip update. They require `expectedVersion`, preserve the Trip/manifest on unschedule and audit before/after windows.
- Availability is a window-scoped read model only. PostgreSQL constraints and transactional revalidation remain authoritative for overlap, eligibility and race outcomes; the UI never submits manually entered Driver/Vehicle UUIDs.
- G3C3 recommendations are ephemeral deterministic read models, not persisted decisions. The canonical score is capacity 45 + consolidation 20 + early window 20 + route quality 10 + origin-aligned Driver 5, with stable business-code/ID tie-breaks.
- Recommended create is still an explicit Dispatcher/Admin command. The backend ignores recommendation score as authority and atomically revalidates resource eligibility/ownership, half-open reservation, exact-route Transfer/Shipment state and integer capacity before creating only a `PLANNED` trip.
- Shipping-fee online payment is a separate aggregate from COD and uses a provider-neutral contract. `PENDING → PAYMENT_PENDING → PAID` is committed only by a verified webhook/IPN; browser return is read-only, and a paid fee maps to the existing pickup/delivery obligation without cash collection or COD mutation.
- Production payment integration stays disabled until a canonical vendor, credentials/secrets storage, callback contract, compliance, billing and release plan are explicitly approved. H3 intentionally stops with only the contract and development/test adapter; wallet, invoice and refund are out of scope.
